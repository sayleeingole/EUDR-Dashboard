# 07 — Audit trail and quality assurance

The design guarantees that any conclusion, checklist item, or export can be traced backwards to evidence, decisions, and the person who made them — at any later date, including after yearly changes.

## Audit log

Every state change writes an audit event: **who** (operator identity), **when** (timestamp), **what** (event type + affected record), **before/after** snapshot, and **why** where a reason is mandatory. Logged event types include:

| Category | Events |
|---|---|
| Evidence | imported (batch + origin), manually entered, approved, rejected (+reason), superseded, re-confirmed for cycle |
| Sources | added to whitelist (+reason), retired (+reason) |
| Assessments | rating suggested (rule trace), confirmed, overridden (+reason), narrative saved, section signed (version), section reopened (+reason) |
| Legal | instrument added, candidate created, refined relevant/not relevant (+reason), verification document linked/unlinked |
| Rules | rating rule or mitigation rule created/edited/retired (versioned; old versions kept) |
| Checklist | generated (with input versions), marked stale |
| Cycle | opened, closed, reopened (+reason), roll-forward executed |
| Export | every export: type, scope, file name, generated by/at |
| Research | run started (scope, template version), completed (batch file), failed |

The audit log is **append-only and spans all cycles**. The Audit trail tab provides filtering (by country, section, event type, actor, date range) and xlsx extract.

## Append-only guarantees

- No UPDATE or DELETE operations exist in the application code paths for evidence, decisions, sign-off versions, rule versions, or audit events. Corrections are superseding records; withdrawals are status changes with reasons.
- Sign-off versions freeze their **evidence set**: the exact records (by ID) a rating/narrative was based on. Superseding evidence later never rewrites history — it flags the section for review instead.
- Checklists record the versions of all inputs at generation time.
- The SQLite file is included in routine backups (OneDrive folder location provides versioned copies); periodically, a dated read-only copy is archived at cycle close.

## Operator identity

Each app session runs under a named operator (Windows username by default, confirmed at start). All decisions carry this identity. If colleagues use the tool later (intranet deployment), individual identities are required — shared accounts are not acceptable for sign-offs.

## Quality assurance checks

**Built into the workflow (enforced by the app):**
- No rating without approved evidence or an explicit "insufficient basis" manual rating with reason.
- Mandatory reasons on: rejection, override, not-relevant refinement, cycle reopen, source changes.
- Unlisted sources blocked until the source is approved (two-step control).
- URL spot-check obligation flagged on records feeding a `high` suggestion (see `03`).
- Final exports only from fully signed assessments; otherwise watermarked DRAFT.
- Stale-flags when inputs change under a signed section or generated checklist.

**Periodic (operator-driven, recorded as QA events):**
- **Sample re-verification**: each cycle, a sample of approved evidence records is re-opened against their sources.
- **Rule review**: the rating and mitigation rule libraries are reviewed once per cycle so codified judgment stays current with regulation and guidance.

## Export conventions

All exports: `KLK_EUDR_<country>_<region|ALL>_<cycle>_<doctype>_<YYYYMMDD>.<ext>`
Doctypes: `RiskAssessment`, `Art9Checklist`, `DeltaReport`, `AuditExtract`. Every export event is logged with the exact file name, so any document in circulation can be matched to the system state that produced it.

## What an auditor can be shown

1. The signed risk assessment report for a cycle, per section: rating, narrative, sources.
2. For any statement in it: the approved evidence records, their sources and retrieval dates, and who approved them when.
3. For any rating: the rule trace of the suggestion and the human confirm/override with reason.
4. For any checklist item: the requirement and/or risk conclusion that generated it, and the rule version used.
5. For any year: what changed from the previous year and why (delta report).
6. The complete decision log for any of the above (audit extract).
